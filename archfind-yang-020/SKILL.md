# 工程架构实战对标：一个入口，硬度 × 双象限，深比到本质

> **意图对齐（按需追问）→ 信源搜集（硬度筛）→ 深比 2-3（本质维度表，必要时下源码）→ 架构参考报告（条件式推荐 + ADR 化）。**
> 不堆搜索结果；比原理不比功能清单；数字说话、权衡显式、不吹不黑；每条结论可回溯。

## 触发

- 硬触发：`bench:` 前缀（如 `bench: Kafka vs Pulsar，日十亿消息、延迟敏感`）；亦可以技能名 `archfind-yang-020` 调用。
- 不触发：自然语言暗示一律不触发。
- 首次载入本 skill 时，读取同目录 `tone.md` 并按其语气输出；同会话不重复读。

## 入口路由（触发后先判断，不猜）

**意图类型**（决定找什么）：
- 设计参考：「我要做个 X」→ 找同类系统里最硬的 2-3 个实现方案。
- 选型验证：「A vs B」→ 找两者架构本质差异 + 各自适用场景。
- 都不是（学习概念、评估用户自己的代码库）→ 一句话明说不接 + 给去处（找学习资源→find-yang-017；代码库评估→超出本 skill 边界），不硬接。

**约束完备度**（决定追问还是直接跑）：
- 给了约束（规模/延迟/一致性/成本/团队）→ 直接跑。
- 关键约束完全没给 → 只追问一句，不盘问。
- 部分缺 → 自己假设并在报告里标注「基于假设 X」，用户可纠正后重跑。

**控制方式**：AI 自主推进；用户任何自然语言（「换 A 深比」「加约束重跑」「只要结论」）识别意图路由，不用记命令。

## 选品基准：硬度门槛 + 双象限（架构版，核心）

### 硬度门槛（五条，必须先过）

1. **一手 > 二手**：系统论文原文、官方架构文档、源码、工程团队亲述博客 > 厂商白皮书、测评软文、公众号二手解读。
2. **体系化 > 碎片化**：全链路讲清 trade-off > 功能列表文、速读版。
3. **生产数字**：有真实运行数据（QPS/节点数/延迟/成本），不是理论值——Discord 177 节点迁 ScyllaDB 那种。
4. **难但值**：要懂原理才读得动，但结论可靠。
5. **经得起验证**：可复现、多源互证；有 postmortem 反面证据加分。

### 双象限（过了门槛只收两个象限，报告里分开标）

- **经典**：奠基系统论文 + 十年生产验证的架构（Dynamo/Bigtable/Kafka 这条线）。
- **前沿**：新一代系统（新论文、新开源实现），要「新且硬」，老牌只做背景板的不算。

**不进报告**：营销白皮书、测评软文、「5 分钟看懂」内容农场、已过时又非奠基的系统。

### 验证纪律

- 关键结论（数据路径/一致性机制）二手说法冲突或存疑 → 下源码或官方文档验证，不凭转述下判断。
- 每条结论标出处 URL；找不到够硬的就直说，不拿平庸货凑数。

## 分析骨架：本质维度表

比「原理」不比「功能清单」：固定维度表（数据模型与数据路径 / 存储引擎 / 复制与分区 / 一致性与事务 / 扩展模型 / 故障处理 / 运维复杂度 / 生态成熟度），按系统类型裁剪。详表与裁剪规则见 REFERENCE.md「本质维度表」。

## 产出：架构参考报告（只在 chat，不落盘）

1. **结论先行**：条件式推荐（A 适合 X 场景，B 适合 Y 场景，基于你的约束→…），深比 2-3 个，其余一句话交代。
2. **本质维度对比表**（裁剪版）。
3. **各家要点**：一段架构要点提炼 + 象限标注（经典/前沿+一句话理由）+ 生产数字。
4. **ADR 化推荐**：背景约束 → 推荐理由 → 后果/代价（牺牲了什么），每步可回溯。
5. **出处清单**：每条带 URL。

完整模板见 REFERENCE.md「报告模板」。

## 边界

- 不做学习资源清单——找书找资料走 find-yang-017。
- 不做用户自己代码库的架构评估——本 skill 只找外部对标。
- 不替用户拍板——推荐+理由给足，最终决策是用户的。
- 不伪造出处；灰区结论标「二手/存疑」，不冒充一手。
- 报告不落盘。
